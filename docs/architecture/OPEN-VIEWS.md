# fluid Open Views — protocol v1

Any tool (Pharo, Python, Node, a business service) can describe the views of its own objects in an
open JSON format and serve them over HTTP; fluid shows them with no plugin to write. The format is
fluid's own, shaped like GT's Phlow views (typed views, priority, lazy items, actions, forward).
Spec-Fluid (Pharo) is one provider of the protocol. Epic: badetitou/fluid#44.

- Zod schemas (the source of truth): `packages/shared/src/openViews/` (`items.ts`, `nodes.ts`,
  `protocol.ts`), exported by `@fluid/shared`.
- JSON Schema for providers in other languages: [`open-views.schema.json`](open-views.schema.json),
  generated by `pnpm --filter @fluid/shared schema:open-views` (a test fails when it is out of date).

## Routes

`<base>` is the provider's base URL, entered by the user (e.g. `http://localhost:8081/spec-fluid`).
`<id>` is the object's id, URL-encoded. Bodies are JSON (`application/json`, UTF-8).

| Route | Response (`$defs` name) | Phlow equivalent |
|---|---|---|
| `GET <base>/.well-known/fluid-views` | `Discovery` | — |
| `GET <base>/objects/<id>/views` | `ObjectViewsResponse` | `getViewsDeclarations` |
| `GET <base>/objects/<id>/views/<key>` | `ViewResponse` | `asDictionaryForExport` |
| `GET <base>/objects/<id>/views/<key>/items?path=&offset=&limit=` | `ViewItemsResponse` | `retrieveItems:fromIndex:` |
| `POST <base>/objects/<id>/views/<key>/actions/<actionId>` | `ViewActionResult` | `actionSpecifications` |
| `POST <base>/objects/<id>/evaluate` (capability `evaluate`) | `Evaluation` | — |

### Discovery

```json
{ "protocol": "fluid-views", "version": 1, "name": "Moose", "capabilities": { "actions": true, "evaluate": true } }
```

`protocol` and `version` are fixed. fluid refuses any other version. A missing capability means that it
is not supported, and fluid does not call its route.

### Views of an object

```json
{
  "object": { "id": "42", "type": "FamixJavaClass", "label": "Collection" },
  "views": [
    { "key": "source", "title": "Source", "priority": 5 },
    { "key": "methods", "title": "Methods", "priority": 10 }
  ]
}
```

`key` is unique for the object and stable across calls. fluid shows views by **`priority`, smallest
first**. When two views have the same priority, it keeps the order in which they were sent.

### One view

```json
{
  "key": "methods", "title": "Methods", "priority": 10,
  "view": { "kind": "columnedList", "columns": [{ "title": "Method" }], "items": [], "lazy": true },
  "actions": [{ "id": "refresh", "label": "Refresh", "icon": "reload" }]
}
```

## Refs

`ref: { id, type? }` points to an object **in the GraphQL source** fluid is connected to. `id` is the
object's GraphQL id, and `type` is its concrete GraphQL type when it is known. When the user clicks
something that carries a ref, fluid opens that object. Cells, items, SVG hotspots, `forward` nodes,
action results and evaluations can carry a ref.

## View nodes

A view is a tree of `ViewNode`s, told apart by `kind`:

| kind | Fields | Notes |
|---|---|---|
| `list` | `items`, paging | one cell per item |
| `columnedList` | `columns: [{title}]`, `items`, paging | one cell per column; old `table` |
| `tree` | `columns?`, `roots`, paging | items nest through `children` |
| `text` | `text`, `language?`, `highlights?: [{start,end}]` | 0-based offsets, `end` exclusive |
| `svg` | `svg`, `hotspots?: [{ref,x,y,width,height}]` | viewBox coordinates; fluid sanitises the SVG |
| `label` | `text` | short inline text |
| `composite` | `direction: row\|column`, `children` | layout of other nodes |
| `tabs` | `tabs: [{title, node}]`, `selected?` | old `notebook`; `selected` is 0-based |
| `diff` | `before`, `after`, `beforeLabel?`, `afterLabel?`, `language?` | |
| `forward` | `ref`, `view?` | shows the views of another object (only the view whose key is `view` when given) |
| `unsupported` | `type`, `message?` | a provider-side view that cannot be exported; `type` is its name there |

An **item** (`ViewItem`) is `{ cells: [{text, ref?}], ref?, children?, hasChildren?, truncated? }`. The
last three fields only mean something in a tree. Unknown fields are ignored, so a provider can add fields
without breaking fluid.

## Lazy items and paging

`list`, `columnedList` and `tree` take three optional paging fields:

- `total`: how many items (or roots) exist in all. If fewer were sent, fluid fetches the rest from the
  items route.
- `lazy: true`: no item is sent, and fluid fetches all of them from the items route.
- `truncated: true`: the provider cut the data and **cannot** page it. fluid shows that it is incomplete.

In a tree, an item with `hasChildren: true` and no `children` is expanded on demand through the items route.
An item with `truncated: true` has more children than it sent and cannot page them.

**Items route.** `path` names what to page, as dot-separated 0-based indices:

1. The first index is the pageable node (`list`, `columnedList` or `tree`) in the view, counted in document
   order. The walk is depth first; composite children are visited in order, and tabs are visited in order.
2. The following indices walk a tree: a root, then that root's child, and so on.

For example, `0` is the items of the first list, and `1.3.0` is the children of child 0 of root 3 of the
second pageable node. `offset` defaults to 0, and `limit` is chosen by the provider when absent. The response
is `{ "items": [...], "total": 300 }`. It returns the slice `[offset, offset+limit)` and, when known, the
full count.

## Actions

A view lists its actions as `{ id, label, icon?, confirm? }`. If `confirm` is `true`, fluid asks the user
before running the action; if it is a string, fluid asks with that text. Actions need the `actions`
capability. Running an action is a `POST` with no body, or `{}`. The response is
`{ refresh?, ref?, message? }`: `refresh` reloads the view, `ref` opens an object, and `message` is shown
to the user.

## Evaluate (optional)

The `evaluate` capability lets the user run code on an object: `POST …/evaluate` with
`{ "code": "self methods size" }`. The response is `{ display, ref?, items?, truncated? }`.

## Errors

Every error is answered with `{ "error": "<human message>", "code": "<machine reason>" }`:

| Status | `code` | When |
|---|---|---|
| 400 | `bad-request` | invalid query (e.g. a malformed `path`) or body |
| 404 | `object-not-found`, `view-not-found`, `action-not-found` | unknown id, key or action |
| 422 | `evaluation-failed`, `action-failed` | the code or action ran and failed |
| 501 | `not-supported` | a capability the provider did not announce |
| 500 | `internal` | anything else |

## Versioning

`version` changes only for breaking changes. Adding optional fields, node kinds or capabilities stays
within v1. fluid shows a node kind it does not know as `unsupported`.
